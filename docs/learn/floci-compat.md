## Setup notes

- chat-lite runs its own Floci container (`floci-chat`, volume `chat-floci-data`) on port 4566; only one project's Floci runs at a time and `npm run floci:up` refuses while another holds the port.
- `cdk bootstrap` and `cdk deploy` work unchanged with `AWS_ENDPOINT_URL=http://localhost:4566`.
- Floci serves AWS hostnames under `*.localhost.floci.io:4566` (public DNS → 127.0.0.1), over plain http/ws: execute-api as `<id>.execute-api.localhost.floci.io:4566`, Function URLs as `<id>.lambda-url.us-east-1.localhost.floci.io:4566`. Those names come from public DNS, so with the internet down they don't resolve (`getaddrinfo ENOTFOUND`): the socket, stream and run int tests and the smoke fail together while plain `localhost:4566` calls still work. Rerun once the network is back.
- WebSocket API: `$connect`/`$disconnect`/`$default` and `postToConnection` work, but the management call must go to the API's own host (`http://<apiId>.execute-api.localhost.floci.io:4566/<stage>/@connections/<id>`); Floci's main endpoint answers `UnknownOperationException`. `services/src/spike/ws.ts` `callbackEndpoint()` picks it when `AWS_ENDPOINT_URL` is set.
- Response streaming (Floci 2.4.0): a `RESPONSE_STREAM` Function URL returns the streamed status + headers but an **empty body** (`content-length: 0`), and `InvokeWithResponseStream` is not implemented (`UnknownOperationException`). Locally, a run's SSE stream is served by a small Node HTTP server on `http://localhost:4600` (`npm run dev` starts it with the web app; `npm run stream:local` on its own) that calls the same `streamRun` as the stream Lambda, and the threads Lambda's `STREAM_URL` points there; on AWS the Function URL streams for real.
- Lambda durable functions run on Floci: checkpointed steps, a durable `wait` (the function is not running), invoke by alias with `DurableExecutionName`, and `GetDurableExecution` for the result.
- A Lambda can start a durable execution on Floci: the threads Lambda's asynchronous `Invoke` (`InvocationType: "Event"`, `DurableExecutionName`) of the run function's `live` alias starts the run loop, and a failing step's retries (`createRetryStrategy`, about a second apart) replay and resume as on AWS. Locally checked by `services/src/runs/run.int.test.ts`.
- EventBridge Scheduler one-time `at(...)` schedules fire on Floci (a few seconds late, like AWS) with a role assumed by `scheduler.amazonaws.com`.
- Floci returns Function URLs as `<id>.lambda-url.us-east-1.127.0.0.1:4566`, which `new URL()` rejects; call them as `<id>.lambda-url.us-east-1.localhost.floci.io:4566`.
- CDK: naming a `WebSocketLambdaIntegration` "Default" collides with the `$default` route's logical ID (`SectionAlreadyContains`); use distinct names.
- S3 presigned URLs: a Lambda's own S3 endpoint is an address inside Docker, so URLs for the browser are signed against `S3_PUBLIC_ENDPOINT=http://localhost:4566` with path-style addressing. Floci enforces what matters here: the POST policy's `content-length-range` (an 11 MB upload gets 400), bucket CORS (an unlisted origin's preflight gets 403), and the signed `response-content-type` / `response-content-disposition` overrides on GET.
- CDK `autoDeleteObjects` fails on Floci: its custom-resource Lambda calls S3 on port 443 (`ECONNREFUSED`), which Floci doesn't serve. The local files bucket uses `RemovalPolicy.DESTROY` without it.
- Floci rewrites its whole DynamoDB store (`/app/data/dynamodb-items.json`) on every write, so writes slow down as test data piles up: about 5 ms per read but 350 ms per write at 14,000 items (8 MB). When the integration suites start timing out, reset the Floci volume (its data is disposable) and deploy again.
- Floci answers any `/ws/...` path on an execute-api host itself (an empty 403, `/ws` alone gives 500) before routing, so no HTTP API route may live under `/ws/`; the ticket route is `POST /live/ticket`.
- WebSocket `$disconnect` after a clean client `close()` reaches the Lambda anywhere from about 1 s to over 20 s later on Floci (closing the page is prompt), so offline presence can lag locally.
- Floci's GSI queries see writes at once, and no run has raised `TransactionConflict`, so GSI lag and clashing concurrent transactions don't show up locally.
- Model keys: the run Lambda reads its provider keys from the Secrets Manager secret `cl-<stage>-model-keys` (JSON with `ANTHROPIC_API_KEY`, `DEEPSEEK_API_KEY`, `DEEPSEEK_BASE_URL`), never from its environment. Floci serves Secrets Manager, and its CloudFormation creates an `AWS::SecretsManager::Secret` as on AWS (with a random 32-character placeholder value until one is put) and deletes it with the stack; `PutSecretValue` and `GetSecretValue` round-trip. A Floci Lambda's own `GetSecretValue` works, and its container reaches `api.anthropic.com` and DeepSeek's `/anthropic` endpoint: a live run on Floci (Haiku, DeepSeek Flash and Auto, 2026-11-11) answered on all three. A plain `deploy:local` leaves the last keys in the secret, so put `{}` into it after a live session. Locally the run Lambda uses the fake models unless deployed with `npm run deploy:local -- --live-models`, which sets `MODEL_GATEWAY=live` and then copies the three keys from the repo's `.env` into Floci's secret (they never pass through CDK or `cdk.out`). On AWS the secret's value is set out of band.
- Floci ran 25 durable executions at once (the load test, `npm -w services run test:load`) with no failures; send→done p95 was 57 s, mostly DynamoDB writes queued one at a time.
- Floci doesn't roll back a failed stack update ("Rollback is not implemented"): the stack stays `UPDATE_ROLLBACK_FAILED`, and `ContinueUpdateRollback` doesn't clear it. Delete the stack and deploy again (Floci data is disposable). The delete itself fails while the files bucket holds objects (`DELETE_FAILED`, "bucket … is not empty"), so empty it first: `aws --endpoint-url http://localhost:4566 s3 rm s3://cl-local-files --recursive`. One way into this state: an update that recreated an HTTP API route Floci still held ("Route with key 'PUT /rooms/{roomId}/model' already exists").
- Every checkout deploys the same `cl-local-core` stack to the one Floci, so the stack runs whatever was deployed last, and deleting it (the rollback fix above) also deletes its user pool, so signed-in sessions and test users vanish. Deploy right before an int or smoke run, and run one checkout's suites at a time.
- Room files: on Floci, server-side `CopyObject` (staging → `workspaces/`) copies the bytes and the content type exactly, `DeleteObjects` (quiet) deletes and reports no errors, and the presigned POST into `staging/` works like the attachments one. The bucket's lifecycle rule (`staging/` expires after 1 day) is stored and read back by `GetBucketLifecycleConfiguration`, but nobody has watched Floci actually expire an object, so on Floci treat the expiry as unverified.
- Sandbox: Floci has no AgentCore, so the local run Lambda (`SANDBOX_KIND=docker`) calls the sandbox server on this machine at `SANDBOX_URL=http://host.docker.internal:4700`. Docker Desktop routes that name from Floci's Lambda containers to the host even though the server binds `127.0.0.1` only, so no `0.0.0.0` bind or bridge-gateway URL is needed (checked by `services/src/runs/sandbox.int.test.ts`, which starts the server itself when none is listening). The Lambda sends `Host: host.docker.internal:4700`, which the server accepts, and the token from `.secrets/sandbox-token` that `deploy:local` bakes into its environment; another worktree's deploy replaces that token, so redeploy from the worktree whose server runs. An online sandbox container can reach Floci through the bridge gateway (Floci listens on all interfaces and takes any credentials), so the local sandbox server starts every session offline unless it was started with `SANDBOX_LOCAL_INTERNET=1`; never combine that with `deploy:local --live-models`, which puts real model keys into Floci's Secrets Manager.

## Setup notes

- chat-lite runs its own Floci container (`floci-chat`, volume `chat-floci-data`) on port 4566; only one project's Floci runs at a time and `npm run floci:up` refuses while another holds the port.
- `cdk bootstrap` and `cdk deploy` work unchanged with `AWS_ENDPOINT_URL=http://localhost:4566`.
- Floci serves AWS hostnames under `*.localhost.floci.io:4566` (public DNS → 127.0.0.1), over plain http/ws: execute-api as `<id>.execute-api.localhost.floci.io:4566`, Function URLs as `<id>.lambda-url.us-east-1.localhost.floci.io:4566`. Those names come from public DNS, so with the internet down they don't resolve (`getaddrinfo ENOTFOUND`): the socket, stream and run int tests and the smoke fail together while plain `localhost:4566` calls still work. Rerun once the network is back.
- WebSocket API: `$connect`/`$disconnect`/`$default` and `postToConnection` work, but the management call must go to the API's own host (`http://<apiId>.execute-api.localhost.floci.io:4566/<stage>/@connections/<id>`); Floci's main endpoint answers `UnknownOperationException`. `services/src/spike/ws.ts` `callbackEndpoint()` picks it when `AWS_ENDPOINT_URL` is set.
- Response streaming (Floci 2.4.0): a `RESPONSE_STREAM` Function URL returns the streamed status + headers but an **empty body** (`content-length: 0`), and `InvokeWithResponseStream` is not implemented (`UnknownOperationException`). Locally, a run's SSE stream is served by a small Node HTTP server on `http://localhost:4600` (`npm run dev` starts it with the web app; `npm run stream:local` on its own) that calls the same `streamRun` as the stream Lambda, and the threads Lambda's `STREAM_URL` points there; on AWS the Function URL streams for real.
- Lambda durable functions run on Floci: checkpointed steps, a durable `wait` (the function is not running), invoke by alias with `DurableExecutionName`, and `GetDurableExecution` for the result.
- A Lambda can start a durable execution on Floci: the threads Lambda's asynchronous `Invoke` (`InvocationType: "Event"`, `DurableExecutionName`) of the run function's `live` alias starts the run loop, and a failing step's retries (`createRetryStrategy`, about a second apart) replay and resume as on AWS. Locally checked by `services/src/runs/run.int.test.ts`.
- Durable child contexts work on Floci: `ctx.runInChildContext` (SDK 3.0.0) checkpoints a helper agent's steps under the child and the child's own result, and `GetDurableExecutionHistory` lists `ContextStarted` / `ContextSucceeded` around the child's `StepStarted` / `StepSucceeded` events. A helper that waited on an approval (`waitForCallback` inside the child) resumed in a new invocation that replayed the child from its checkpoints: no step name started twice (checked by `services/src/runs/helpers.int.test.ts`, 2026-11-12). So helpers run in child contexts locally too, with no fallback.
- Durable callbacks work on Floci: `ctx.waitForCallback` suspends the run, `SendDurableExecutionCallbackSuccess` from another process wakes it within a second or two, and the callback's own `timeout` fires a `CallbackTimeoutError` on time. So approvals use the callback locally too, with no polling substitute. Locally checked by `services/src/runs/approval.int.test.ts`.
- A Lambda's async-invoke config deploys on Floci: CDK's `configureAsyncInvoke` on the push worker becomes an `AWS::Lambda::EventInvokeConfig`, and `GetFunctionEventInvokeConfig` reads back `MaximumRetryAttempts: 0`, `MaximumEventAgeInSeconds: 300`. A plain `InvocationType: "Event"` invoke of `cl-<stage>-push` answers 202 and runs the worker (checked 2026-11-11). Whether Floci honours the retry count wasn't checked: AWS's retries come a minute or more later.
- Floci doesn't enforce IAM, so a role missing `lambda:SendDurableExecutionCallbackSuccess` still wakes runs locally; the grants (run, live and threads functions) are pinned by infra tests instead.
- Tool keys: the run and connections Lambdas read the GitHub App and Tavily keys from `cl-<stage>-tool-keys` (JSON with `TAVILY_API_KEY`, `GITHUB_APP_ID`, `GITHUB_APP_SLUG`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_APP_CLIENT_ID`, `GITHUB_APP_CLIENT_SECRET`), which `npm run deploy:local -- --live-tools` fills from `.env` and the PEM file that `GITHUB_APP_PRIVATE_KEY_PATH` names. Without the flag the tools run in fake mode (`TOOL_MODE=fake`: canned GitHub, Tavily and pages, no network). Floci's Lambda containers reach `api.github.com` and `api.tavily.com`: a live run on Floci (2026-11-11) searched with Tavily, listed the App's installations, and posted an approved comment through the App. As with the model keys, put `{}` into the secret after a live session.
- Push keys: the push worker reads the VAPID keys from `cl-<stage>-push-keys` (JSON with `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`), and the push routes read only `cl-<stage>-push-public-key` (JSON with `VAPID_PUBLIC_KEY`), so the Lambda facing browsers never holds the private key. `deploy:local` stores both whenever `.env` has them, since they cost nothing and a browser needs the public key to subscribe even while sends are fake (`PUSH_MODE=fake`). `npm run deploy:local -- --live-push` sends through the real push services and fails fast if a key is missing.
- Push secrets start as JSON: CloudFormation's `GenerateSecretString` with `secretStringTemplate: "{}"` and `generateStringKey: "unset"` gives `cl-<stage>-push-keys` and `cl-<stage>-push-public-key` the value `{"unset":"<random>"}` on Floci too, so before any keys `GET /push/key` answers `{publicKey: null}` (checked 2026-11-12), and after `deploy:local` stores them the same warm routes Lambda returns the real key.
- Floci's Lambdas reach the browser push services: with `--live-push` (2026-11-12) the worker POSTed to `fcm.googleapis.com` for a real subscription made by headless Chrome (no failure logged after the first send, which failed with a bare `Error`, likely the cold first connection inside the 5 s send timeout) and for a made-up FCM endpoint, which FCM answered as gone, so the worker deleted that device. Headless Chrome never received the push (its push channel doesn't deliver), so arrival on a device is a hand check. Headless Chrome also can't subscribe in an incognito-like context (`Registration failed - permission denied`); the browser's default context can.
- Transcribe and Polly are faked locally, not run on Floci. Dictation streams to a Node server on `ws://localhost:4601` (`scripts/src/transcribe-local.ts`, started by `npm run dev`) that speaks Transcribe's event-stream frames: one more word of a fixed sentence per half second of audio as a partial under one `ResultId`, the final on an empty `AudioEvent`, an exception frame for a bad query or frame. The voice Lambda signs that URL in fake mode (`TRANSCRIBE_LOCAL_URL`). Read aloud uses a fake speaker that returns one second of silent MP3 (`VOICE_MODE=fake`). The real presigned host, port 8443 and Polly are checked only on AWS (`voice.live.test.ts`).
- S3 user metadata round-trips on Floci (`PutObject` `Metadata` → `HeadObject` `Metadata`), which the image step's retry reads Gemini's cost from, and a `HeadObject` on a deleted key reads as missing (the code treats AWS's 403-without-ListBucket and 404 the same).
- The connection from this machine to `api.github.com` drops some connects (about one in four timed out after 10 s on 2026-11-11, from the host's `curl` too), so a GitHub call is tried again, 3 times in all, when its connection never opened. Rerun once the network is steady rather than reading a "GitHub couldn't be reached" step as a Floci fault.
- EventBridge Scheduler one-time `at(...)` schedules fire on Floci (a few seconds late, like AWS) with a role assumed by `scheduler.amazonaws.com`.
- Recurring Scheduler `cron(...)` schedules with `ScheduleExpressionTimezone` fire on Floci at the right wall clock: `cron(15 21 * * ? *)` in `Asia/Kolkata` fired at 15:45:02Z (21:15 IST), `cron(* * * * ? *)` fired every minute about 2–3 s after it, and an `UpdateSchedule` in place to `cron(49 10 * * ? *)` in `America/New_York` stopped the per-minute fires and fired at 15:49:02Z (2026-11-11, a throwaway Lambda target, `FlexibleTimeWindow OFF`, a `RetryPolicy`). A DST change can't be watched live, so how Scheduler treats a skipped or repeated wall-clock time is taken from the AWS docs (a skipped time doesn't run, a repeated one runs once) and pinned by the cadence unit tests, not by Floci.
- Scheduler fills `<aws.scheduler.scheduled-time>` in a Lambda target's `Input` on Floci as on AWS: `"at":"2026-11-11T15:44:00Z"` (whole seconds, `Z`, no milliseconds). The schedule fire handler claims each occurrence by that time, so a redelivered fire is a duplicate.
- `UpdateSchedule`, `GetSchedule` and `DeleteSchedule` on a missing name throw `ResourceNotFoundException` (`Schedule not found: <name>`) on Floci, so the trigger's update-then-create (Scheduler has no upsert) and its "already gone" delete work locally. `GetSchedule` returns the expression, zone and input as sent.
- Waiting for a real cron is slow, so `npm run schedule:fire -- <roomId> <scheduleId>` invokes `cl-local-schedule-fire` directly with `at` = now, as Scheduler would at the schedule's time. It only ever talks to Floci. Two fires within one minute are one occurrence, so the second reads `duplicate`.
- Floci doesn't check DynamoDB reserved words: `ProjectionExpression: "timeZone"` and `SET timeZone = :tz` run there, while AWS refuses them (`TIMEZONE` is reserved). Expressions name every attribute through `#placeholders`, which works on both; a local pass proves nothing about this.
- Floci returns Function URLs as `<id>.lambda-url.us-east-1.127.0.0.1:4566`, which `new URL()` rejects; call them as `<id>.lambda-url.us-east-1.localhost.floci.io:4566`.
- CDK: naming a `WebSocketLambdaIntegration` "Default" collides with the `$default` route's logical ID (`SectionAlreadyContains`); use distinct names.
- S3 presigned URLs: a Lambda's own S3 endpoint is an address inside Docker, so URLs for the browser are signed against `S3_PUBLIC_ENDPOINT=http://localhost:4566` with path-style addressing. Floci enforces what matters here: the POST policy's `content-length-range` (an 11 MB upload gets 400), bucket CORS (an unlisted origin's preflight gets 403), and the signed `response-content-type` / `response-content-disposition` overrides on GET.
- CDK `autoDeleteObjects` fails on Floci: its custom-resource Lambda calls S3 on port 443 (`ECONNREFUSED`), which Floci doesn't serve. The local files bucket uses `RemovalPolicy.DESTROY` without it.
- Floci rewrites its whole DynamoDB store (`/app/data/dynamodb-items.json`) on every write, so writes slow down as test data piles up: about 5 ms per read but 350 ms per write at 14,000 items (8 MB). When the integration suites start timing out, reset the Floci volume (its data is disposable) and deploy again.
- Floci answers any `/ws/...` path on an execute-api host itself (an empty 403, `/ws` alone gives 500) before routing, so no HTTP API route may live under `/ws/`; the ticket route is `POST /live/ticket`.
- WebSocket `$disconnect` after a clean client `close()` reaches the Lambda anywhere from about 1 s to over 20 s later on Floci (closing the page is prompt), so offline presence can lag locally.
- Floci's GSI queries see writes at once, and no run has raised `TransactionConflict`, so GSI lag and clashing concurrent transactions don't show up locally.
- Model keys: the run Lambda reads its provider keys from the Secrets Manager secret `cl-<stage>-model-keys` (JSON with `ANTHROPIC_API_KEY`, `DEEPSEEK_API_KEY`, `DEEPSEEK_BASE_URL` and, for the image tool, `GEMINI_API_KEY`), never from its environment. Floci serves Secrets Manager, and its CloudFormation creates an `AWS::SecretsManager::Secret` as on AWS (with a random 32-character placeholder value until one is put) and deletes it with the stack; `PutSecretValue` and `GetSecretValue` round-trip. A Floci Lambda's own `GetSecretValue` works, and its container reaches `api.anthropic.com` and DeepSeek's `/anthropic` endpoint: a live run on Floci (Haiku, DeepSeek Flash and Auto, 2026-11-11) answered on all three. A plain `deploy:local` leaves the last keys in the secret, so put `{}` into it after a live session. Locally the run Lambda uses the fake models unless deployed with `npm run deploy:local -- --live-models`, which sets `MODEL_GATEWAY=live` and then copies the four keys from the repo's `.env` into Floci's secret (they never pass through CDK or `cdk.out`). On AWS the secret's value is set out of band.
- Floci ran 25 durable executions at once (the load test, `npm -w services run test:load`) with no failures; send→done p95 was 57 s, mostly DynamoDB writes queued one at a time.
- Floci doesn't roll back a failed stack update ("Rollback is not implemented"): the stack stays `UPDATE_ROLLBACK_FAILED`, and `ContinueUpdateRollback` doesn't clear it. Delete the stack and deploy again (Floci data is disposable). The delete itself fails while the files bucket holds objects (`DELETE_FAILED`, "bucket … is not empty"), so empty it first: `aws --endpoint-url http://localhost:4566 s3 rm s3://cl-local-files --recursive`. One way into this state: an update that recreated an HTTP API route Floci still held ("Route with key 'PUT /rooms/{roomId}/model' already exists").
- Every checkout deploys the same `cl-local-core` stack to the one Floci, so the stack runs whatever was deployed last, and deleting it (the rollback fix above) also deletes its user pool, so signed-in sessions and test users vanish. Deploy right before an int or smoke run, and run one checkout's suites at a time.
- Room files: on Floci, server-side `CopyObject` (staging → `workspaces/`) copies the bytes and the content type exactly, `DeleteObjects` (quiet) deletes and reports no errors, and the presigned POST into `staging/` works like the attachments one. The bucket's lifecycle rule (`staging/` expires after 1 day) is stored and read back by `GetBucketLifecycleConfiguration`, but nobody has watched Floci actually expire an object, so on Floci treat the expiry as unverified.
- Sandbox: Floci has no AgentCore, so the local run Lambda (`SANDBOX_KIND=docker`) calls the sandbox server on this machine at `SANDBOX_URL=http://host.docker.internal:4700`. Docker Desktop routes that name from Floci's Lambda containers to the host even though the server binds `127.0.0.1` only, so no `0.0.0.0` bind or bridge-gateway URL is needed (checked by `services/src/runs/sandbox.int.test.ts`, which starts the server itself when none is listening). The Lambda sends `Host: host.docker.internal:4700`, which the server accepts, and the token from `.secrets/sandbox-token` that `deploy:local` bakes into its environment; another worktree's deploy replaces that token, so redeploy from the worktree whose server runs. An online sandbox container can reach Floci through the bridge gateway (Floci listens on all interfaces and takes any credentials), so the local sandbox server starts every session offline unless it was started with `SANDBOX_LOCAL_INTERNET=1`; never combine that with `deploy:local --live-models`, which puts real model keys into Floci's Secrets Manager.
- MCP token key: Floci's CloudFormation honours `GenerateSecretString` on `cl-local-token-key`: the value is 64 letters and digits (`passwordLength: 64, excludePunctuation: true`), not the 32-character placeholder a secret without a generator gets. It survives redeploys and goes with the stack, so a Floci reset leaves every stored MCP sign-in unopenable (each connection then reads as needing a reconnect). DynamoDB on Floci runs the token store's writes as written: `SET sealed = :sealed ADD #version :one` inside a transaction (1 for a new item, +1 on a reconnect), the conditional `#version = :read` save, and a `DeleteItem` with `ReturnValues: ALL_OLD` under `#ttl > :now`. From the host, `host.docker.internal` resolves to the LAN address, where a server bound to `127.0.0.1` isn't listening, so tests on the host pass `guardedFetch` a `lookup` that maps it to 127.0.0.1; Floci's Lambdas reach `http://host.docker.internal:4710` directly (checked by invoking `cl-local-mcp-connections` through a full OAuth connect against the test server).
- OAuth and MCP endpoints: Floci's HTTP API routes public paths under `/.well-known/` to their Lambda like any other (`/.well-known/oauth-authorization-server`, `/.well-known/oauth-protected-resource` and `…/mcp` all answer 200), so no local substitute is needed and the issuer is the API's own host, `http://<apiId>.execute-api.localhost.floci.io:4566`. A form-encoded body (`application/x-www-form-urlencoded`) reaches the Lambda base64-encoded with `isBase64Encoded: true`, as on AWS, while a JSON body arrives as plain text (checked with a throwaway echo Lambda); the handlers decode whenever the flag is set.
- OAuth rate limits: every caller on this machine reaches Floci's HTTP API from the same `requestContext.http.sourceIp`, so the per-address allowances (20 registrations and 60 authorize requests an hour) are shared by the int tests, the smoke and any manual client. The smoke deletes the `RATE#oauth#…` items before it counts to the 21st registration, and again after. On AWS behind CloudFront the same field holds the edge's address, not the viewer's, which is a step 11 item.
- Bursts and cold containers: Floci retires idle Lambda containers within minutes and starts a fresh one for each concurrent call, so five thread starts sent at once (the smoke's numbering check) can each wait for new `threads` and `run` containers. In the step 8 runs, most took 0.5–1 s alone but up to about 8 s in a burst, and in 3 of 7 smoke runs one passed the web BFF's 8 s API timeout and came back as an empty 500 (the BFF now answers a JSON 504). A cold `next dev` page or a large Floci store adds to it. The numbering check now sends its burst straight to the API with a 30 s deadline, API Gateway's own integration ceiling, since the BFF's 8 s is a budget for a person waiting, not for the counter it checks. The store's size matters more than cold starts: on a fresh store a burst of five took 1.3–2.7 s, but after two full int runs (a 6.5 MB store) three of five passed the threads Lambda's own 10 s timeout and came back as API Gateway 500s, because Floci queues the writes and rewrites the store on each. So run the smoke on a fresh Floci (reset after the int suites), not after them.
- Cognito `AdminGetUser` works on Floci, from the host and from a Lambda: it answers `Enabled: false` after `AdminDisableUser` and `UserNotFoundException` after `AdminDeleteUser`, so the OAuth refresh's account check runs locally as on AWS (checked by `services/src/lib/users.int.test.ts` and a refresh through the deployed token endpoint in `services/src/mcp/server/mcp.int.test.ts`).
- `dynamodb:LeadingKeys` conditions aren't enforced either (no IAM at all), so the OAuth Lambda's table scope is pinned by `infra/lib/oauth.test.ts` only; the real check is on AWS.
